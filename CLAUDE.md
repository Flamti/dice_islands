# Dice Islands — правила работы над проектом

Пошаговая градостроительная стратегия с механиками настольных игр (кубики, риск-менеджмент, набеги) на летающих островах. Low-poly 3D, ар-нуво + стимпанк.

## Роли

- **Пользователь** — системный архитектор и геймдизайнер. Принимает все решения по архитектуре, структуре данных, игровому циклу и дизайну.
- **Claude** — ведущий программист. Пишет чистый, оптимизированный, рабочий код по спецификациям.
- Не принимать самостоятельных архитектурных решений. При сомнениях в связях между компонентами — остановиться и спросить пользователя.

## Стек

- **Движок:** Godot 4.7.1 (бинарник: `resources/Godot_v4.7.1-stable_linux.x86_64`, системный `godot` 4.7 в PATH, офлайн-документация: `resources/godot-docs-html-master/`).
- **Языки:** GDScript — визуал, звук, UI; C++ — игровое ядро (EnTT ECS) через GDExtension.
- **ОС:** Linux (пути, shell-скрипты — под Linux).

## Архитектура (высокоуровнево)

- Вся игровая логика — в изолированном C++ ядре (ECS на EnTT). Godot отвечает только за рендер, звук и ввод.
- Обмен движок ↔ ядро — через интерфейс-адаптер, только плоские данные (dt, ввод, ссылки на ассеты).
- Модули процедурной генерации независимы от визуала, экспорт в GLB без привязки к сцене.
- Компоненты — только данные (structs), системы — только логика, сущности — ID.

## Стандарты кода

- Никаких магических чисел: параметры — в константы или экспортируемые переменные.
- Краткие комментарии к сложной математике и неочевидным ветвлениям.
- Целевое железо: мобильный уровень (RTX 3050 Mobile / встроенная графика); в перспективе VR. Не допускать утечек памяти в C++.
- Не использовать устаревший синтаксис по памяти — сверяться с офлайн-документацией в `resources/godot-docs-html-master/`.

## Строгие запреты

- **Никаких заглушек:** не оставлять `// TODO`, `pass`, недописанные функции, если явно не запрошен черновик. Код готов к компиляции.
- **Не ломать рабочее:** новая фича не переписывает существующий рабочий код в других файлах без необходимости интеграции.
- **Никаких галлюцинаций API:** при неуверенности в существовании метода — сказать прямо, а не выдумывать.

## Сборка и проверка

- `scripts/build.sh` — сборка C++ ядра (scons) + `--import` для регистрации GDExtension.
- `scripts/test.sh` — unit-тесты чистого ядра (g++ + ASan/UBSan, без Godot).
- `scripts/gd_check.sh` — headless-загрузка проекта, проверка ошибок скриптов.
- `scripts/net_smoke.sh` — интеграционные тесты сети (лобби; партия двух людей с барьерами, таймерами и островами).
- `scripts/gen_check.sh` — CLI-генератор острова: сборка без Godot, GLB повторяем байт-в-байт.
- Запуск игры: `godot --path game` (или бинарник из `resources/`).

## Технические нюансы (пополняются по ходу этапов)

- У godot-cpp **нет ветки 4.7**: сабмодуль на master, сборка против API-дампов из нашего бинарника 4.7.1 (`core/extern/api/`, опция `gdextension_dir`, дампы закоммичены). EnTT закреплён на v3.9.0.
- Рантайм грузит GDExtension **только** из `res://.godot/extension_list.cfg`, который создаёт импорт редактора — поэтому build.sh запускает `--import`. Ключ `[native_extensions]` в project.godot не работает.
- Самый первый `--import` на холодном `.godot` разово падает на выходе (после регистрации расширения); повторные запуски чистые, build.sh детектит успех по наличию extension_list.cfg.
- RPC рассылаются при poll в конце кадра: мгновенный `disconnect_peer` после `rpc_id` обгоняет пакет — отклонённого гостя кикаем с задержкой `KICK_DELAY_SEC`.
- `--check-only` проверяет скрипт в отрыве от проекта и не видит autoload-синглтоны — для проверки использовать gd_check.sh (полная headless-загрузка).
- ID игрока в партии = индекс слота лобби; все команды входят в ядро через `submit_intent(player_id, intent)`, соответствие peer → слот хранит только хост (`net_session.gd`). Каждый `core/tests/test_*.cpp` — отдельный бинарник со своим `main()` (см. test.sh).
- Данные строительной сетки считает ядро при генерации (сканирование столбцов поля плотности, а не Godot-raycast) — Godot только отображает оверлей. Динамика сетки (клетки-леса от платформ, оставшиеся POI) и эффективные капы (с учётом складов) едут в снапшоте игрока; статичный оверлей buildable/blocked рисуется один раз из начальной сетки, POI и леса — снапшот-driven в `island_view`. Бонус мельницы (`food_bonus`) считается при сборе пула через `systems/adjacency` и виден в снапшоте кубика. UV — зеркальная укладка (mirror repeat) внутри сегмента атласа 2×2: непрерывна, швов от fract нет. У Marching Cubes порядок эмиссии индексов 0-2-1 (наша плотность положительна внутри — обход зеркалится относительно таблиц Бурка).
- В `_broadcast_*` NetSession сначала RPC, потом локальный emit: обработчик локального сигнала может слать новые RPC, и они не должны обгонять сам стейт.
- Победа (`systems/victory`, SPEC §10, фаза Проверок): выбывание игрока при разрушении замка (`alive=false`, `castle_destroyed`), затем победитель по приоритету Чудо → Военная → Культурная. Военная/культурная требуют ≥2 команд (`has_opponents`) — иначе соло/кооп-партия «побеждала» бы военным путём мгновенно и рушила одиночные тесты; Чудо доступно любой команде. При победе `MatchState.finished=true`, стейт-машина стоит (проверка в начале `tick` и в теле цикла). Чудо — многоэтапная стройка (`Building.wonder_stage`, повторный BuildIntent «wonder» продвигает этап), завершение фиксирует `wonder_complete_turn`, победа — если простояло `turn >= complete+1`. Выбывший игрок остаётся руинами (рейд по нему разрешён — снят чек `alive` в `raid`).
- Катастрофы (`systems/danger`, SPEC §7.2): эффекты через `apply_effect` (кража, молния, болезнь, саботаж, шторм, метеорит, обрушение края, нашествие). Числа — в `DisasterDef.params` из disasters.json. Болезнь распространяется по смежным (`adjacency`) каждый ход; Disabled снимается в фазу 0 по `Building.restore_turn`. Деструктор ландшафта (`gen/destruction` + `generate_island_carved`): вырезанные клетки копятся в `PlayerCarved`, меш ре-полигонизуется (плотность даёт -1000 в вырезанных столбцах) и рассылается через `poll_island_updates`. Тёмная магия: Opponent-катастрофа у человека откладывается в `PendingChoices`, фаза Катастроф держится (turn_machine `HoldPredicate`/`HoldTimeout`, таймаут `kDarkChoiceTimeoutSec`=15с → случайный выбор), `TargetPickIntent` применяет выбор через `EventQueue` (события из submit_intent попадают в поток следующего tick). Упаковка ключа клетки: всегда `static_cast<uint32_t>` перед сдвигом (иначе UBSan — сдвиг отрицательного).
- Боевая симуляция (`systems/combat`) самодостаточна: принимает `BattleSetup` (сетка + здания + группы атакующих), возвращает `BattleResult` (исход + кадры). Детерминизм — на одном бинарнике хоста: RNG расходуется только на уворот (по id бойцов/башен, порядок фиксирован). Пират-рейд ставится катастрофой в фазе 5 в `PendingRaids`, резолвится в фазе 8; логи боёв берутся адаптером через `poll_battles()` и рассылаются клиентам (`battle_ready`) для проигрывания капсулами. Исследования (`systems/research`, SPEC §8): `ResearchIntent` в фазе Развития при активном Университете (`unlocks_research`); узлы ветки открываются последовательно, трата культуры уменьшает `resources.culture` (= счёт культурной победы, культура — один счётчик). Эффекты применяются проверкой `PlayerResearch.has(effect)` в системах: Логистика в `economy.effective_caps`, Инженерия в `expansion`, Тактика/Стратегия в `raid`, Фортификация в `combat/resolve` (стены +HP, per-tower `BattleBuilding.tower_damage`), Ремесло в `apply_research_income` (фаза Ресурсов). Магические узлы определены в research.json, эффекты — этап 12. Числа эффектов — в `params` узла (`ResearchCatalog::param`).
- Рейды игроков: `RaidIntent` в фазе 7 (`systems/raid`) валидирует активный Порт, вместимость, гарнизон (мечи), запрет союзников, лимит рейдов/ход; отправка списывает бойцов из мечей, выжившие возвращаются в фазе Боя. Награду 30% за цель получает лишь группа с последним ударом (`GroupOutcome.got_reward`, трекинг `last_hit_group` в sim). Требование «один сид → один лог» проверяется тестом на двух прогонах. Стартовые мечи задаются в `starting_resources` (в игре 0; в тестах — для гарнизона).
- Эффекты фаз выполняются через `PhaseHook` в `turn::tick` в момент входа в фазу (до продвижения дальше внутри того же тика) — порядок «активация → еда/голод → сбор пула → бросок → конвертация → катастрофы» гарантирован даже при большом dt. Пул кубиков очищается в фазе Катастроф (`systems/danger`), а не в Ресурсах: кресты нужны шкале опасности после конвертации ресурсов. Поэтому в снапшоте пул виден с фазы Дохода по Катастрофы включительно. RNG партии — компонент `MatchRng` (сид от хоста, состояние пойдёт в снапшоты этапа 14), создаётся для любой партии. Общий RNG расходуют несколько систем (бросок кубиков, тасовка голода) — порядок и объём его потребления входят в контракт детерминизма: игроки и здания обходятся в порядке ID, тасовка Фишера–Йетса берёт числа только при реальной нехватке еды.

## Workflow

- Перед новой фичей — сверяться со `SPEC.md`; при расхождениях уточнять у пользователя, а не додумывать.
- После правок `.gd` — проверять синтаксис headless-запуском Godot.
- Двигаться вертикальными срезами по этапам `PLAN.md`, не реализовывать все системы разом.
- **Git-коммит после каждого успешного этапа.**
- Проектные документы: `SPEC.md` (игровая спецификация), `REQUIREMENTS.md` (требования), `PLAN.md` (этапы). При потере контекста новой сессии: «Прочитай наши документы и скажи, на каком этапе из PLAN.md мы остановились».
